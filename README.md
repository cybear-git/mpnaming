# Генератор названий карточек товара (ПРОМПТ v5 → Python)

Программа построчно обрабатывает выгрузку товаров и формирует колонку
**«Название для МП»** по правилам ПРОМПТ v5, а веса признаков подбирает сама —
обучаясь на колонке с эталонными названиями.

Промпт превращён в четыре отдельных файла, и это главная идея архитектуры —
каждый можно скачать, отправить заказчику или нейросети и загрузить обратно
через веб-интерфейс (раздел «Настройки»), не трогая остальной проект:

| Файл | Что содержит | Кто правит |
|---|---|---|
| `data/dictionaries.json` | значения полей → формулировки, роды, товарные группы | человек, без программиста |
| `data/bans.json` | запреты и стоп-слова: что не становится признаком, что вырезается, что не рекомендуется | человек, без программиста |
| `data/rules.json` | параметры логики генерации: коридор длины, пороги разбора состава, особые случаи вида изделия | человек, аккуратно — часть значений структурные |
| `data/weights.json` | насколько нужен каждый признак — глобально и по каждой группе | обучение |

Код (`namer/*.py`) задаёт только порядок шагов и алгоритм обучения — все
конкретные значения, пороги и списки читаются из этих четырёх файлов.

## Установка

```bash
pip install -r requirements.txt
```

Нужны только `pandas`, `openpyxl` и (для веба) `flask`.

## Консольные режимы

```bash
# 1. Обучение на файле с колонкой «Эталонный ответ»
python run.py train Обучение.xlsx --epochs 10 --reset

# честная проверка: 20 % строк модель не видит при обучении
python run.py train Обучение.xlsx --epochs 10 --reset --holdout 0.2

# 2. Обработка файла → xlsx со всеми исходными столбцами + «Название для МП»
python run.py process Товары.xlsx -o результат.xlsx

# 3. Наглядный контроль: эталон рядом с результатом
python run.py review Обучение.xlsx --limit 40
python run.py review Обучение.xlsx --only-errors -o сравнение.xlsx

# 4. Метрики по товарным группам — видно, где словарь слабый
python run.py eval Обучение.xlsx

# 5. Чего не хватает словарям: значения полей без правил
#    и слова из эталонов, которые скрипт не воспроизводит
python run.py report Обучение.xlsx

# 6. Разбор одной строки: какие признаки взяты, с какими весами и почему
python run.py explain Товары.xlsx --row 42
```

## Веб-приложение

```bash
python webapp.py     # http://127.0.0.1:5000
```

Загрузка файла → таблица «эталон / результат» на экране → кнопка «Скачать xlsx».
Вторая форма на странице дообучает модель на файле с эталонными названиями.

### Настройки (`/config`)

Раздел «Настройки» — редактор всех четырёх файлов конфига прямо в браузере,
без доступа к серверу и без программиста:

- **Словари** (`/config/dictionaries`) — форма «добавить/изменить значение»
  (колонка выгрузки, значение, слот, формулировка, при необходимости формы
  по родам) со списком уже добавленных значений и удалением; плюс текстовый
  редактор всего файла для остальных секций (`fabric`, `fiber_*`, `extras`,
  `head_rules`, `group_head`, `gender`, `head_translate`, `head_implies`).
- **Веса** (`/config/weights`) — таблица весов с поиском по подстроке ключа,
  правкой и удалением прямо в таблице, плюс форма «добавить/изменить один
  вес» и текстовый редактор всего файла.
- **Правила** (`/config/rules`) — форма для основных параметров (коридор
  длины, порог основного волокна в составе, штраф материалу из «Состав» при
  известной ткани, штраф словам из `discouraged_words`) и текстовый редактор
  для остального (`fill_order`, `slot_capacity`, пороги по волокнам, особые
  случаи вида изделия, лексикон обучения).
- **Запреты** (`/config/bans`) — по списку на каждую из четырёх категорий
  (`stop_values`, `head_forbidden`, `banned_phrases`, `discouraged_words`),
  по одному значению на строку.

На каждой странице — «Скачать файл» и «Загрузить файл» (с проверкой перед
сохранением: если файл не проходит те же проверки, что использует сам
генератор, он не будет сохранён и старый файл останется на месте). Правки
применяются сразу, без перезапуска приложения — CLI и `/process` каждый раз
читают файлы заново.

## Как это работает

1. **Вид изделия** (`features.determine_head`). Порядок как в разделе 2 промпта:
   поле «Вид изделия» → перевод английских значений → справочник Group NEW →
   родовое слово дивизиона. Плюс лексикон, выученный из эталонов: если для
   группы 62 заказчик пишет «Футболка вязанная», программа запомнит именно это.
2. **Кандидаты-признаки** (`features.build_candidates`). Каждое непустое поле
   строки превращается в кандидата: слот (1–13 по разделу 4), формулировка из
   словаря, согласованная по роду с видом изделия. Состав разбирается по
   процентам (порог 65 %, «из вискозы» / «с содержанием шерсти»), название ткани
   имеет приоритет над составом.
3. **Отбор весами** (`model.Model`). Каждый кандидат получает оценку
   `приоритет + вес_глобальный + вес_по_группе`. Признак попадает в название,
   если оценка выше калиброванного порога.
4. **Сборка** (`generator.generate`). Порядок строго по разделу 4, сильные
   модельные особенности идут сразу после вида изделия (п. 1.1), не влезающий
   признак пропускается, при длине меньше 30 включается добор по п. 11.2,
   в конце — гарантия заполнения по п. 12. Пустых ячеек не бывает.

### Обучение

Усреднённый перцептрон с зазором. Для каждой строки с эталоном программа
смотрит, какие кандидаты реально попали в эталонное название, и двигает веса
тех, что отобраны неверно. После обучения автоматически подбирается порог
отбора признаков. Веса пишутся отдельно для каждой товарной группы, поэтому
«со спущенным плечом» может быть нужным в W30 и лишним в W10.

Дообучение накопительное: `python run.py train новый_файл.xlsx` без `--reset`
продолжает с текущих весов.

## Как сравниваются названия

Сравнение посимвольное давало ложные «нет»: одинаковые по смыслу названия
считались разными из-за порядка слов, окончаний и опечаток заказчика.
Теперь `review` и `eval` выдают вердикт по существу:

| Вердикт | Что означает |
|---|---|
| `да` | тексты совпадают с точностью до регистра, ё/е, пунктуации и пробелов |
| `опечатки` | все слова и их порядок совпадают, разница в окончаниях или опечатках («визскозы» = «вискозы») |
| `порядок` | тот же набор слов, отличается только порядок |
| `почти` | расхождение ровно в одном слове |
| `нет` | расхождение больше одного слова |

В таблице сравнения есть колонки **«Не хватает слов»** и **«Лишние слова»** —
по ним сразу видно, чего не хватает словарю. Первые три вердикта считаются
совпадением по существу.

## Текущее качество (1040 эталонных строк)

| Метрика | Значение |
|---|---|
| Точное совпадение | 18.8 % (на отложенных строках 11.5 %) |
| Совпадение по существу | 21.3 % |
| Совпадение по словам (token F1) | 0.727 (на отложенных 0.702) |
| Вид изделия угадан | 93 % |
| Вне коридора 30–60 символов | 0 |
| Пустых ячеек | 0 |

Потолок словаря — 84 %: столько слов эталона в принципе есть среди кандидатов.
Разрыв между 84 % и 0.727 — это работа весов, разрыв выше 84 % — работа словаря.

100 % недостижимы в принципе: эталон местами противоречит сам себе. Рабочие
метрики — token F1, доля «почти» и глазной контроль через `review`.

## Расхождения промпта v5 с эталоном (учтено в проекте)

Промпт местами жёстче, чем реальная практика заказчика. Проверено по 1040
эталонным строкам:

| Что говорит промпт | Что в эталоне | Что сделано |
|---|---|---|
| «больших размеров», PLUS — запрещены | 0 упоминаний в эталоне, но 59 раз в старых названиях с сайта | запрет оставлен, он подтверждён данными |
| «базовая», «офисная» — жёстко ограничены | «базов» 84 строки, «офисн» 43 | сняты из запретов, теперь это обычные признаки: включать или нет решают веса. Раньше скрипт ставил «базовая» 360 раз, стало 134 |
| «повседневный», «нарядный» — запрещены | «повседневн» 4, «нарядн» 4 | убраны из запретов, перенесены в `discouraged_words`: такое слово получает штраф `discouraged_penalty` (`data/rules.json`) и реже предлагается моделью, но не вырезается, если уже пришло другим путём |
| длина строго 30–60 | 82 названия заказчика короче 30 символов | 30 остаётся целью, но есть `soft_min` = 24: если добрать длину можно только слабым признаком, название остаётся коротким, а не разбавляется словом «базовая» |
| «вязаный» — только группы 7K/7Y/84 | 115 строк по всей W60 | слово доступно всей W60 как обучаемый признак |
| «экокожа» запрещена | 15 упоминаний в эталоне | запрет оставлен: «из искусственной кожи» — это осознанная правка заказчика |

Запреты живут в `data/bans.json` → `banned_phrases` и удаляются целыми
оборотами, а не отдельными словами, поэтому соседние слова больше не рвутся.

> До этой правки `discouraged_words` был мёртвым полем: значения из него
> загружались, но нигде не использовались, поэтому «повседневный»/«нарядный»
> и всё, что туда добавляли, продолжало предлагаться моделью на общих
> основаниях. Теперь штраф `discouraged_penalty` действительно применяется
> при сборе кандидатов (`features.build_candidates`).

### Ручки настройки длины (`data/rules.json` → `length`)

| Параметр | Значение | Смысл |
|---|---|---|
| `min` | 30 | целевая нижняя граница из промпта |
| `soft_min` | 24 | ниже этой длины название не опускается никогда |
| `max` | 60 | жёсткий потолок |
| `fill_floor` | −0.4 | минимальный вес признака, который можно добавить ради длины. Поднимите ближе к 0 — названия станут короче и точнее по словам; опустите — все уложатся в 30–60, но появится «вода» |

## Что выверено по эталонным строкам

Каждое правило проверено на 1040 эталонных названиях — считалась точность
(как часто значение поля действительно даёт эту формулировку) и покрытие.

**Добавлено, потому что подтвердилось данными**

| Правило | Точность по эталону |
|---|---|
| колонка «Состав» как источник материала: `Вискозасодержащие` → «из вискозы» | 77 % |
| `Полиэстер/Вискоза` → «из поливискозы» | 59 % при покрытии 91 % |
| `Вид полотна = Трикотаж` → «трикотажные» | 98 % |
| `Вид брюк = Jogger` → вид изделия «Брюки-джоггеры» | 10 из 10 |
| `Вид изделия = Поло` → «с длинным рукавом» | 10 из 10 |
| `artwork` в группе 41 → «с вышивкой» | 11 из 11 |
| `Силуэт = Mom fit` в дениме → «зауженные к низу» | 11 из 16 |
| `Рисунок материала = Фактурная вязка` → «крупной вязки» | 12 из 38 |
| `Состав = PU` → «из искусственной кожи» | 75 % |

**Отключено, потому что данные противоречат промпту**

| Значение поля | Что было | Что в эталоне |
|---|---|---|
| `Вид рукава = Реглан` | «реглан» | 0 упоминаний из 45 строк |
| `Вид рукава = Без рукава` | «без рукавов» | 0 из 15 |
| `Длина = Короткое / Короткая` | «укороченная» | 1 из 101 |
| `Длина = Длинное / Длинная` | «макси» | 0 из 37 |
| `Стиль = Occasion` | «нарядная» | 1 из 106 |
| `Рисунок = Blocking` | «с колорблокингом» | 0 из 11 |
| `Воротник = R-neck` | «R-neck» | 10 из 239 |

Такие правила не удалены, а получили отрицательный стартовый вес: если на новых
данных заказчик начнёт их использовать, обучение вернёт их само.

**Найдено и исправлено при разборе данных в этом заходе**

| Проблема | Причина | Что сделано |
|---|---|---|
| «лён» никогда не попадал в название | ключи `fiber_main`/`fiber_genitive`/`valuable_fibers` нормализуются (ё→е → «лен»), а название волокна из разбора состава оставалось с «ё» — словарь и код искали разные строки | `composition.parse_composition` нормализует имя волокна сразу при разборе |
| «Вид воротника/Капюшон» = «Воротник» — 138 строк без правила | это базовый/дефолтный воротник, заказчик его никогда не называет отдельно (проверено — только 6 упоминаний «воротник» в эталоне из 95 строк, и все не про этот случай) | добавлено в `stop_values` (`data/bans.json`), больше не висит в `report` как незакрытый пробел |
| материал по «Состав» (словарная колонка) конкурировал с материалом по названию ткани на равных | приоритет «ткань важнее состава» (п. 5.1 промпта) был реализован только для разбора процентов состава (`Composition`), но не для словарной колонки «Состав» | штраф `composition.fabric_priority_penalty` (`data/rules.json`) теперь действует на обе колонки одинаково |

**Чего добиться нельзя из текущей выгрузки**

«вязаный» (51 строка), «на молнии» (33), «со спущенным плечом» (24),
«крупной вязки» (частично) — в выгрузке нет поля, которое их предсказывает.
Например, «вязаный» стоит в 115 строках из 310 по дивизиону W60, и ни одна
колонка не отделяет их от остальных: это решение редактора. Максимум, что здесь
можно сделать, — угадывать по группе, что и делает секция `extras`.

## Как улучшать дальше

1. `python run.py report файл.xlsx` показывает, каких значений нет в словарях и
   какие слова эталона программа не умеет произносить. Это готовый список задач.
2. Добавить значение в `data/dictionaries.json` (секция `features`), указав слот
   и формулировку — при необходимости в четырёх формах `{m, f, n, p}`. Проще
   всего это сделать через веб-интерфейс, `/config/dictionaries` — не нужно
   руками редактировать JSON и следить за синтаксисом.
3. Переобучить: `python run.py train Обучение.xlsx --epochs 10 --reset`
   (или кнопка «Дообучить модель» на главной странице веб-приложения).
4. Проверить: `python run.py eval Обучение.xlsx` — по каким группам стало лучше.

Пути к файлам конфига можно переопределить у любой команды CLI: `--dictionaries`,
`--bans`, `--rules`, `--weights` — удобно для сравнения экспериментальных версий
файла без изменения `data/`.

Секция `extras` — это формулировки, которых нет ни в одном поле выгрузки
(«вязаный», «на резинке», «крупной вязки»). Они предлагаются модели как
кандидаты при выполнении условия `when`, а включать их или нет — решают веса.

## Известные ограничения

- В выгрузке нет полей «застёжка» и «карманы», поэтому «на молнии» и
  «с накладными карманами» программа может только угадывать по группе и типу
  полотна. Если эти поля появятся в выгрузке — качество заметно вырастет.
- Согласование по роду сделано таблицей форм в словаре, а не морфологическим
  анализатором. Для нового прилагательного нужно указать четыре формы.
